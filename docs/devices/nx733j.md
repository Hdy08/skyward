# Nubia Z70 Ultra (`NX733J`)

This experimental port uses the working NX733J TWRP included in the owner's
local `NX733J_HyperOS_3.0.307.6_A16_7.28.zip`. Display, touch, encrypted Data,
vibration, screen-off/wake and WLAN have passed owner validation on that
installed custom ROM. This is an NX733J hardware profile; the custom system's
Xiaomi product properties are not used to select another phone's drivers.

## Reference device and recovery base

The bootloader reports `sun`, unlocked `yes`, current slot `a`, and a
104857600-byte `recovery_a`. The device uses a Snapdragon 8 Elite and a
`6.6.92-android15-8-g3637f4904cf5-ab13944661-4k` GKI kernel. Its installed
system reports Android 16 and vendor interface 35. The installed system's
security patch adopted for credential services is `2026-05-01`.

`devices/nx733j.toml` pins the complete 100 MiB donor recovery with SHA-256:

```
12523342021fcf258c7bba092ca82b1d31073794fb0b5080f613a06393ea9b60
```

Both recovery partitions originally read from the phone match that image. The
base uses boot header v4, has no kernel, and includes the working recovery
runtime and touch firmware. The packer keeps its init, adbd, Binder libraries,
SELinux policy and touch firmware. It removes the donor's copied HAL startup
scripts, duplicate recovery service and generic WLAN/charger actions before
adding the NX733J board script, Skyward executable, configuration and resources.
The generated image has a recovery AVB hash descriptor and a 100 MiB footer.

The retained Binder runtime uses the `SYST` parcel header. The installed
vendor's init and VINTF descriptions supply the actual KeyMint, Gatekeeper and
boot-control services after the installed OS version and security patch have
been adopted. No donor credential service is started ahead of that setup.

The original `recovery_a`, `recovery_b`, `boot_a`, `vendor_boot_a`, `init_boot_a`,
`dtbo_a` and `vbmeta_a` were backed up before testing. The workspace copy and
the external copy in `D:\Flash\NubiaZ70Ultra\Rec\Skyward-backup-20261115` have
size and SHA-256 manifests. The installed vendor boot and init boot differ
from the ZIP's versions; the ZIP versions were not flashed.

## Display and host touch processing

The panel is `DSI-1`, 1216 by 2688, with `panel0-backlight`, parameter
`dsi_display0`, density 480 and no rotation. The configured normal brightness
ceiling is 2047. The display path uses the installed kernel and its native
panel modes.

The `zte_tpd` module exposes `/dev/thp` and `/dev/input_agent`. The vendor's
`/vendor/bin/odm_tsc` processes the raw touch data and creates
`gdix_input_agent`, whose axes span 19455 by 43007. Recovery starts that
program as `system` in the vendor's groups with `SYS_NICE`, using the donor's
retained Goodix firmware and the installed libraries. The device nodes receive
their native owners and access modes. Skyward scales the input coordinates to
the display. The owner confirmed upright display and correct menu touch.

## Encrypted Data and USB

The installed fstab describes f2fs Data, FBE v2 with
`aes-256-xts:aes-256-cts:v2+inlinecrypt_optimized+wrappedkey_v0`, and wrapped-key
metadata encryption. The installed KeyMint and Gatekeeper services are
discovered and started with their own dependencies. The owner entered the
credential only on the device and confirmed decrypted internal storage in
Skyward.

The board script enables configfs USB and selects the bootloader's controller
in peripheral mode. Skyward owns the MTP/ADB functions rather than retaining
the donor's competing FunctionFS setup. The combined USB profile is `mtp,adb`;
the computer opens an MTP session while Recovery ADB remains connected.
The owner confirmed browsing internal storage from the computer after Data
decryption, and the host retained Recovery ADB with `mtp,adb` enabled.

## WLAN preparation

Modules are taken from the running slot's vendor boot, vendor, vendor_dlkm and
system_dlkm rather than copied from the ROM archive. WLAN uses
`qca_cld3_peach_v2`; its firmware configuration is aliased from
`/vendor/etc/wifi/peach_v2/WCNSS_qcom_cfg.ini`. The modem firmware is mounted
at the expected paths and `cnss/fs_ready` is signalled after module loading.

Driver preparation runs in the background after the first UI frame. On the
reference device the initial calibration took about 10.5 seconds while the UI
remained available. The interface stays down until WLAN is enabled. Once
prepared, the tested enable-to-scan path took about 1.1 seconds. The installed
`wpa_supplicant` provides its AIDL service. The connectivity probe follows the
installed custom ROM. The owner confirmed connection and Internet access.

## Awinic vibration

This device exposes `haptic_hv`/`aw8692x` and `/dev/awinic_haptic`, without an
evdev force-feedback motor. The configured `aidl` haptics backend starts the
installed `vendor.qti.hardware.vibrator.service` as its native system account
and supplies its `RICHTAP_DEVICE_PATH` and `ENV_RICHTAP_CONFIG_PATH` values.
Other devices continue to use the default force-feedback backend.

The reference HAL reports capabilities `0x3`, no named effects and no amplitude
control. Skyward therefore uses the HAL's finite `on` pulse. Its strength
slider varies the pulse duration from about 15 to 29 ms across this profile's
configured range; it does not claim to control unsupported hardware amplitude.
HALs that advertise named effects or amplitude control use those capabilities.

The installed driver's duration thresholds are 20, 30 and 60 ms. Its log
confirms that 20--29 ms selects RAM waveform 2, whereas 30--59 ms selects
waveform 1. The owner found waveform 1 weaker at the top of the initial slider
range. This profile caps the normalized strength at 0.875 so the basic AIDL
pulse mapping ends at 29 ms. A longer timeout on this HAL is not a continuous
increase in amplitude; feedback follows the driver's discrete waveform bands.
The owner retested approximately 50%, 90% and 100% after the limit correction
and confirmed that the top of the slider no longer becomes weaker, with
screen-off and single-key wake still working.

The vendor init script gives the system account write access to `duration_aw`,
`activate_aw`, `activate_mode`, `index`, `seq`, `loop` and `gain`. Applying all
seven permissions is necessary: omitting `activate_mode` caused the native HAL
to reject the pulse. Initial vibration failures were fatal to the UI, which
produced the black screen observed during the first integrated test. Haptics
initialization and playback errors are now logged without terminating the UI.
The owner confirmed menu vibration and screen-off/wake after the permission
fix. No raw gain, voltage or resonance override is used.

## Build and validation

The charging overlay shown about a second after a cabled startup was caused
by treating an unavailable battery reading as an unplugged cable. On this
phone the driver can report its first valid reading after the menu appears,
which then looked like a new cable insertion. The common UI now keeps the
last known cable state: its first valid observation establishes a baseline,
and missing observations retain that baseline. The startup sample is used for display;
event tracking begins with a fresh sample after USB initialization, including
samples whose values have not changed. Stale startup samples are ignored.
The initial observations must remain known and unchanged for two seconds
before cable events are armed: the OnePlus USB enumeration can briefly report
an offline supply even while the cable remains attached. An unknown or changed
observation restarts this background settling period; it never blocks the UI.
Subsequent known changes still animate or wake the screen. Four regression
tests cover startup, a late first reading while dark, real reinsertions across
missing readings, and startup USB enumeration. The donor charger declarations
are unchanged by this fix.

The power-supply collector also preserves `EAGAIN` as an unknown state rather
than an offline supply. Any known online source establishes that power is
supplied; an offline result requires that no remaining source is still
starting. An uncertain result asks the existing reading worker to retry and
retains the last battery sample. Failed initial samples also restart the
settling period. Eight device-information tests include supply aggregation
and temporarily unreadable driver states.

On 2026-11-15 the owner verified this fix on both NX733J and OnePlus 13:
startup with USB continuously connected no longer opens the charging overlay;
display, touch and battery status remain correct. Unplugging and reinserting
the cable still opens the normal charging animation and returns to the menu.
Startup logs contain no cable events, while the physical unplug/reinsert
records one offline and one online event on each device. The four charging
regressions and eight information tests passed on Android; the 47 Windows
configuration/packer tests and Android workspace Clippy also passed.

The verified 104857600-byte image is
`D:\Flash\NubiaZ70Ultra\Rec\Skyward-0.3.1-nx733j-charger-fix.img`, SHA-256:

```text
eee7668304292c6416e1ade77988df53a4ead42beb133f6a7585aabc5a77221e
```

Only `recovery_a` was written and its full readback matches the image;
`recovery_b` and `boot_a` retain their pre-test hashes. The adjacent
`.img.sha256`, `.validation.json` and
`Skyward-0.3.1-nx733j-charger-fix-notes.md` record the checks and owner results.

Build on Windows with the Android ARM64 Rust target, an Android NDK and LZ4:

```powershell
./scripts/build-nx733j.ps1 -Base <verified-recovery.img> -Ndk <android-ndk> -Lz4 <lz4.exe>
```

The script checks the pinned donor hash, builds the packer, Recovery and static
system-init helper, writes `target/nx733j/skyward-nx733j-experimental.img`, and
writes its SHA-256 sidecar. It does not flash a device.

The final build passed Android workspace Clippy with warnings denied, 32
configuration tests, 13 packer unit tests, two packer integration tests, and
27 service-discovery tests run on Android, including the existing phone
fixtures. Independent image verification checked the AVB hash, complete image
size, embedded binary and configuration, static system-init, and preservation
of 3926 donor files outside the deliberate replacements and removals.

Only `recovery_a` was written during this port. Each write was made from root
Recovery ADB, with the target identity, slot, partition size, previous hash and
uploaded image checked first, followed by a full partition SHA-256 readback.
The bootloader reports unlocked but rejected standard `fastboot flash` with
`unknown command`; that attempt left the original partition hash unchanged.
Do not infer support for Fastboot flashing from the unlock flag alone.

## Validation limits

The tested environment is the owner's installed custom ROM and current kernel,
vendor boot, firmware and vendor partitions. Compatibility with stock Nubia
ROMs or other kernel/vendor combinations has not been established.

No Nubia official OTA provider is configured. The Xiaomi identity reported by
the custom ROM does not enable a Xiaomi OTA provider on this device. Official
online query, download and installation are outside this port's validation.
The generic local installer remains available, but ROM installation, partition
restore and kernel installation have not been exercised on this phone.
